Abstract

In contemporary higher education institutions, engineering capstone projects represent a critical milestone in assessing student technical competency, teamwork, and problem-solving abilities. However, conventional manual or semi-automated project management mechanisms—relying on paper registers, fragmented email threads, and generic shared folders—suffer from severe transparency deficits, unauthorized milestone submissions, lack of real-time progress visibility, and administrative overhead during continuous evaluation.

To resolve these challenges, this project presents the Centralized Academic Project Monitoring System, a cloud-native, role-based platform engineered specifically for autonomous engineering colleges. Developed using a robust Spring Boot backend and a reactive modern frontend, the system streamlines the complete project lifecycle across 38 project batches. Key architectural highlights include:

  • Leader-Controlled Submission with Automated Group Synchronization: Enforcing group-level milestone deliverables while keeping all individual team members synchronized in real time.
  • Multi-Format High-Capacity Storage (100MB): Native support for executable ZIP archives, technical PDFs, and MP4 screen recordings.
  • Role-Based Governance Matrix: Granular security boundaries separating Student Leaders, Team Members, Faculty Guides, and Project Coordinators/HODs.
  • Autonomous Institute Branding: Mobile-first responsive interface adhering to institutional design standards.

Chapter 1: Introduction

1.1 Background and Context

Final-year engineering projects demand continuous, phased monitoring across multiple milestones: Topic Selection, Literature Review, Requirement Analysis, Architecture Design, Implementation, Code Review, Testing, and Final Demonstration. Managing 38+ project groups (150+ students) across multiple faculty guides requires a centralized, transparent digital record.

1.2 Problem Statement

Existing academic project workflows suffer from four major bottlenecks:

  • Disorganized Submissions: Files submitted via email lack version control and metadata (timestamp, file hash, group ID).
  • Unequal Accountability: Difficult to determine whether a document was submitted with team consensus or individually.
  • Evaluation Opacity: Faculty rubrics, marks, and feedback are often inaccessible to students until final semester results.
  • Format Restrictions: Traditional LMS solutions block large demonstration videos (.mp4) and source code archives (.zip), restricting evaluation to static documents.

1.3 Objectives of the Proposed System

  • Centralize Lifecycle Management: Unify project registration, guide allocation, milestone tracking, and score calculation under a single portal.
  • Enforce Group Governance: Allow only verified Group Leaders (or authorized delegates) to submit project deliverables, automatically updating the entire group's dashboard upon submission.
  • Facilitate Rich Media Evaluation: Enable direct streaming and download of high-resolution screen recordings, presentations, and code packages up to 100MB.
  • Provide Real-Time Institutional Analytics: Equip the Project Head and HOD with batch-wide performance metrics, pending reviews, and milestone completion percentages.

Chapter 2: System Architecture & Role Matrix

2.1 Role-Based Access Control (RBAC)

Role Portal Access Key Responsibilities & Permissions
Student Leader /student/* Upload 100MB MP4/ZIP/PDF deliverables, delegate upload rights, view synced marks.
Student Member /student/* Auto-synced read access to submissions, view guide feedback, maintain work logs.
Faculty Guide /guide/* Review allocated batches (out of 38), evaluate code & video demos, assign scores.
Project Head / HOD /project-head/* Batch-wide governance, guide allocation, progress analytics, rubric oversight.

2.2 Multi-Tier Technology Architecture

Frontend Layer: React 18, Vite, Tailwind CSS, Responsive Mobile Navigation (Deployed on Vercel CDN)
Backend Layer: Java 17, Spring Boot 3.5.5, Spring Security, JWT (HMAC-SHA256), Hibernate/JPA (Deployed via Docker on Render Cloud)
Persistence Layer: Relational Database with persistent volume mounting for 100MB media assets.

Chapter 3: Implementation & Cloud Deployment

3.1 Key Modules Implemented

  • File Storage Engine: Configured multipart limits (100MB) supporting MP4, MKV, ZIP, RAR, PDF, DOCX, and PPTX with UUID sanitization.
  • Group Auto-Synchronization: Deliverables submitted by the leader update the database at the group level, immediately displaying verified status to all team members.
  • Institute Header UI: Mobile-first responsive header matching official institute branding (Navy Blue #0c2340, Crimson Red divider #c0262d, NAAC A++ accreditation seal).
